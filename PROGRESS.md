## What this is

`fghj` — a local dev orchestration CLI (Rust) + web UI (Svelte) for spinning
up multi-repo "user flow" environments without a monolithic docker-compose or
local k8s. Full product vision: `SPEC.md`.

**`concepts/` is the running index of important design decisions/ideas** —
one file per concept (e.g. `flat-workspace-model.md`,
`fog-of-war-visibility.md`), each with a `## Status` section noting whether
and where it's implemented, and cross-linked via `[[other-concept]]`-style
references. Treat it as required reading before proposing architecture
changes — check whether a concept already covers the idea (or explains why
current behavior is the way it is) before re-deriving it from the code.
**When a new non-trivial design idea/decision comes up, add a new file
here** rather than only describing it in a plan doc or PR — this is the
durable record, plans in `~/.claude/plans/` are not.

## Implemented

- **All three SPEC.md subsystems have a working first cut.** Subsystem A (git
  dependency resolver) is the most mature; Subsystem C's real per-service
  container routing is explicitly deferred (see below).
- **Subsystem B — split-DNS** (`src/dns.rs`): a minimal hand-rolled
  authoritative DNS-over-UDP server for `*.fghj.internal`, answering every
  in-zone `A` query with `127.0.0.1` (NXDOMAIN outside the zone). Binds an
  OS-assigned ephemeral port (`dns::bind`) rather than the SPEC's suggested
  fixed `5353`, which routinely collides with mDNSResponder/Chrome on a real
  dev Mac. `dns::install_os_resolver_config` writes `/etc/resolver/fghj.internal`
  on macOS (`install_macos_resolver`) pointing at that port; Linux/Windows
  print a manual-setup message instead (not implemented). `dns::in_zone` is
  `pub(crate)` and reused by `ca::DynamicCertResolver` so "is this name ours"
  has one definition.
- **Subsystem C — local CA + TLS-terminating reverse proxy** (`src/ca.rs`,
  `src/proxy.rs`): `fghjd` occupies ports 80/443 (`proxy::bind_http`/
  `bind_https`, localhost-only). Port 80 redirects everything to https.
  On 443, `proxy::serve_https` TLS-terminates via `tokio_rustls` (pure-Rust
  `ring` backend — deliberately avoids `aws-lc-rs`/`cmake`), using
  `ca::DynamicCertResolver` (`rustls::server::ResolvesServerCert`) to issue
  and cache a leaf cert per SNI on the fly from a locally-generated CA — a
  single wildcard cert can't work here since X.509 wildcards only match one
  leftmost label (RFC 6125) and names can be arbitrarily deep
  (`a.b.c.fghj.internal`). The CA itself (`ca::ensure_ca`) is generated once
  and persisted at `/var/lib/fghjd/ca/{ca-cert,ca-key}.pem` (durable, survives
  reboot — unlike the pidfile/port file under `/var/run`), and installed into
  the system trust store on macOS (`ca::install_macos_trust`, via `security
  add-trusted-cert`) — kept as a separate step from CA generation so the
  latter stays a pure, testable filesystem operation.
  **`install_macos_trust` is safe to call on every `fghjd` start**, same as
  `dns::install_os_resolver_config`: it first runs `security verify-cert`
  (`ca::is_trusted_on_macos`) — a read-only trust *evaluation*, not a
  modification, so it never triggers a prompt — and only falls through to the
  actual `add-trusted-cert` write when the cert genuinely isn't trusted yet.
  This matters because modifying System keychain trust settings on macOS
  always triggers an interactive Authorization Services password prompt —
  running as root does *not* bypass it (that only bypasses filesystem
  permission checks, not this) — so without the pre-check, a crash-restart
  loop would re-prompt for a password every single restart. The check-first
  design also means trust that's missing for any reason — first-ever run, or
  a user manually revoking it via Keychain Access while the persisted CA
  files remain on disk — self-heals on the next `fghjd` start: it prompts
  exactly once, when (and only when) trust is actually absent. Only
  `https://fghj.internal` (the zone apex) is routed anywhere
  today — relayed via a plain `TcpStream` + `copy_bidirectional` to the
  control API's port. **Everything else in-zone gets a styled "fancy 404"
  placeholder page, not real per-service routing** — routing
  `https://cart.fghj.internal` to an actual running container is explicitly
  deferred to a follow-up (would need SNI → container-port lookup wired
  through `resolver::Node`/`docker.rs`).
  The control API itself no longer has a hardcoded port (the old
  `CONTROL_PORT = 7880` constant is gone): `fghjd` binds it on an OS-assigned
  port and publishes it at `/var/run/fghjd.port`
  (`daemon::write_port`/`read_port`), mirroring the existing pidfile
  convention; the unprivileged `fghj` CLI (`src/main.rs`) discovers it the
  same way instead of hardcoding it, and `fghj wire`'s success message now
  points at `https://fghj.internal/...` instead of a raw `127.0.0.1:<port>`
  URL.
  Schema/resolver support for services with multiple HTTP surfaces (e.g.
  Prometheus's scrape port + admin UI) landed alongside this: `#Service.ports`
  is a map (`{[port]: #Port}`, `#Port: {primary: bool | *false, name?: string}`)
  instead of a plain list — a port's role is declared together with the port
  itself, so a route naming a port the service never declared is structurally
  impossible (no more separate `http_port`/`http_routes` lists to keep in
  sync, and the `resolver`-side cross-reference warning that used to catch
  that mismatch is gone, replaced by a warning if more than one port claims
  `primary`). `primary` puts a port at the service's own derived domain;
  `name` gives one an additional nested domain (see the domain-naming entry
  below). Mirrored into `resolver::ServiceConfig`/`Node` (`PortConfig`). Not
  yet wired into `proxy.rs`'s routing (that's the same deferred
  per-service-routing follow-up above) — currently validated but otherwise
  inert.
- **Uniform, scoped `*.fghj.internal` domain derivation**: no node kind can
  declare its own raw domain anymore (`#Service.internal_domain` is gone,
  `#HttpRoute.domain` is now `#HttpRoute.name`, a bare label). Every node's
  domain — services included — is derived by `runs::start_node` the same
  way, from `node.id` + workspace + run id, so it can never collide the way
  an author-typed string could. `run_id` is always folded in, no exception
  for the default run either (matching `container_name`/network naming,
  which already never dropped it). The one opt-out is
  `#InfraDependency.domain_scope: *"run" | "stable"` — `"stable"` drops the
  run id for that one dependency, a deliberate per-dependency CUE choice
  (e.g. a postgres meant to be the same identity across every run), not an
  implicit bypass. Named ports' domains (`{port.name}.{node's domain}`)
  are now also registered as real Docker network aliases alongside the
  primary domain, so they resolve the same from inside the run's docker
  network and from the host, closing a gap where they only worked from the
  host via fghjd's wildcard DNS.
- **Flat workspace model** ([[flat-workspace-model]] concept): no
  root/component config split — every repo is a peer, any repo can declare
  `flows:`. Implemented in `src/resolver.rs` (`scan_workspace`,
  `resolve_universe`, `pull_all`, `Dependency::Service.local_path`,
  `Node.downloaded`).
- **Fog-of-war visibility** ([[fog-of-war-visibility]] concept): pulled repos
  always render on the graph (dimmed if outside the selected flow) instead of
  only nodes reachable from a flow's declared dependencies.
- **Branch ownership model** ([[branch-ownership-model]] concept): branch
  identity lives on the shared workspace checkout, never on a flow/dependency
  edge, so a diamond dependency can never require two different branches of
  the same repo — the old `path_branches`/"diamond conflict" detector in
  `resolver.rs` was removed as structurally impossible under this model, not
  just avoided. `resolver::git_status_dirty` + `Node.dirty` surface live
  dirty/clean state on the existing "Repos" graph's node cards
  (`GraphView.svelte`) and drawer (`Drawer.svelte`); `App.svelte` polls
  `/universe.json` every 3s while that tab is active. fghj is a passive
  observer — no `fghj branch` command, no UI branch-switch action; you
  `git checkout` normally and the graph just reflects it. There is no
  separate "flow" node/rectangle in the graph — a flow is a highlight lens
  (accent border/edge color) over the shared repo graph, not a node in it.
  Graph layout (`GraphView.svelte`'s `layout()`) is computed once from
  nodes/edges only, independent of the selected flow, and is now
  cycle-safe (DFS drops back-edges before longest-path depth assignment,
  since a hard dependency one way + a flow-scoped dependency the other way
  is a legitimate cycle) and deterministic (`resolve_universe` sorts nodes by
  id before serializing, since `ctx.nodes` is a `HashMap` and would otherwise
  reorder — and therefore visibly jump the layout — on every poll).
- **Run registry** (`src/runs.rs`): named/default runs, per-node branch
  overrides. Default (no override) builds Docker images straight from the
  live workspace checkout; only branch-overridden nodes go through
  `ensure_mirror` + `materialize_checkout` into a throwaway clone under
  `<workspace>/.fghj/`.
- **Docker orchestration** (`src/docker.rs`) and **background download
  jobs** (`src/downloads.rs`) for `pull-all` / per-node pull with status
  polling from the UI.
- **HTTP API + embedded UI** (`src/daemon.rs`, `src/server.rs`): served by the
  root-owned `fghjd` daemon (see Subsystem C above), not by the `fghj` CLI
  directly — `fghj wire [entry] --workspace <dir>` registers a workspace with
  a running `fghjd` (starting it is a separate step: `sudo fghjd`), which
  serves `/workspaces`, `/universe.json`, `/pull-all` (+status), `/pull/:node`
  (+status), `/runs` (list/start/stop), per-node log tailing, and the built
  Svelte UI (`ui/dist`, embedded via `include_dir!`) — reachable at
  `https://fghj.internal` once the TLS proxy is up. The old standalone
  `fghj ui [entry] [--workspace] [--port]` command from earlier sessions no
  longer exists.
- **CUE schema validation** (`fghj validate`): `schema/component.cue` +
  `schema/dependency.cue`, one `#ComponentConfig` shape (no more
  root/component split — matches the flat workspace model above). Requires
  the `cue` CLI on PATH; not vendored.
- **Design system** (`design/`): "Container Yard" visual concept (industrial,
  dark canvas, safety-orange accent) — tokens, guidelines, and a dashboard
  mockup. Not yet fully reconciled against the actual Svelte UI's current
  styling (worth a pass to check drift).

## Known gaps / open questions

- SPEC.md's CLI surface (`fghj setup`, `fghj branch`, `fghj branch set`) does
  not match the implemented CLI (`validate`, `graph`, `wire`, `daemon stop` in
  `src/main.rs`, plus the root-owned `fghjd` daemon binary) — SPEC.md may be
  aspirational/outdated relative to the actual build. Worth clarifying which
  is true before treating SPEC.md as ground truth for CLI behavior.
- `cue` binary is a runtime dependency of `fghj validate` with no vendoring
  or bundled fallback — validate fails hard if it's missing from PATH.
- Subsystem C only routes the zone apex (`https://fghj.internal` → the
  control API) and gives every other in-zone name a placeholder 404 — real
  per-service routing (`https://cart.fghj.internal` → that service's running
  container) is not implemented; see the Subsystem C entry above.
- Subsystem B's OS integration is macOS-only (`/etc/resolver`); Linux
  (`systemd-resolved`) and Windows (NRPT) are unimplemented, per SPEC.md §5.
- `install_macos_trust`/`install_macos_resolver` have no uninstall path wired
  into `fghj daemon stop` beyond removing the DNS resolver file and port/pid
  files — the CA stays installed in the system Keychain across a full
  daemon-stop, by design (so a later `fghjd` restart doesn't need
  re-approval), but there's no explicit "purge everything" command yet.
