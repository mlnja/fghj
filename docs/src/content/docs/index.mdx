## Why fghj?

Testing one user journey shouldn't require booting every microservice you own.
`fghj` reads a small `fghj.yaml` in each repo, follows declared dependencies
outward from whichever repos you're actually working on, and brings up just
that subgraph — with real `*.fghj.internal` HTTPS domains, trusted locally
signed certs, and no `docker-compose.yml` to hand-maintain.

<CardGrid stagger>
  <Card title="Federated config" icon="puzzle">

  <Card title="Real HTTPS, locally" icon="approve-check">

## At a glance

```bash
# Validate a repo's .fghj.yaml against the schema
fghj validate ./.fghj.yaml

# Resolve the full dependency graph from any repo and print it as JSON
fghj graph git@github.com:acme/checkout-service.git

# Register a workspace with the running daemon, then drive it from the UI
fghj wire git@github.com:acme/checkout-service.git
```

```yaml
# .fghj.yaml
version: "1.0"

services:
  checkout:
    build:
      context: .
    ports:
      "8080":
        primary: true
    environment:
      DATABASE_URL: postgres://app:dev@${FGHJ_SERVICE_FQDN:postgres}:5432/app
    dependencies:
      - kind: backing
        name: postgres
        image: postgres:16
        ports: ["5432"]
        healthcheck:
          test: ["CMD-SHELL", "pg_isready -U app"]
          interval: 2
          retries: 15
      - kind: service
        repo: git@github.com:acme/payments-service.git

flows:
  checkout:
    description: End-to-end checkout journey
    dependencies:
      - kind: service
        repo: git@github.com:acme/payments-service.git
```

That repo now answers at `https://checkout.<workspace>.fghj.internal` with a
certificate your system already trusts, and its Postgres at
`postgres.checkout.<workspace>.fghj.raw.internal:5432`. Neither address is
written down anywhere — both are derived.
